## 3. 保存错误：原因与成功路径

实际调用为：保存窗口选择/输入/快捷槽 → trySave → 覆盖确认 → doSave。生成 `save_game.lua:123` 先关闭窗口，126读取未声明的 `IS_3DS`，127才是 `pcall(app.save, ...)`。strict在126立即抛错；该次操作尚未进入序列化或文件提交。

正式owner是 `tools/integration/product_patches.py:656–673` 的R68保存UI注入。模块中没有此局部变量，其他Lua模块的local不能为它提供作用域。全量检索本生成树中6个含IS_3DS的文件，另外5个均有先行文件级声明；本次没有发现第二个同类owner遗漏。

验证盲点：`tests/test_r68_operations.py:212–221` 抽取doSave后人为补了全局 `IS_3DS=true`；`test_handheld_ui.py`只组合旧pinned窗口与handheld变换，未加载全部最终补丁。自动保存/保存退出直接到app.save，跳过UISaveGame入口。这些证据仍覆盖各自链路，不能代表实际窗口可用。

诊断复现已完成：完整生成strict/class/window/file-browser/save/confirm文件，保留真实方法，图形、文件存在性和app.save为明确受控服务。新名、选择已有文件、Slot1/2/3及真实覆盖确认6入口均重现同一126行错误，app.save调用0；覆盖取消正确。独立Lua5.5复现之后，主线程用现有Lua5.4 API-check库复验相同结论（0.050秒）。这属于主机入口链诊断；完整App、原生保存及新版本真机尚未验收。

最小修复：注入块从当前 `app._3ds.operations` 取得保存操作owner，读取它的last结果；桌面/无adapter保留原路径。禁止给整个游戏补一个全局IS_3DS来掩盖依赖。保留提交结果、必要收尾、已显示错误的去重语义；对生成文件的修改全部回到正式owner再生成。

成功契约：实际窗口进入 → 原字符/覆盖规则 → 同一operations实例 → 临时文件写完并关闭 → 原子提交 → 必要收尾 → 一次成功提示 → 重载内容连续。错误保留旧档及原始原因，已提交但收尾失败单独表达。真实生成文件+strict必须成为入口测试的固定基础。

### 3.1 有界扩大审查：把共同原因与成功路径一起固定

用户要求从根本原因决定扩大范围。本次按证据扩到三条共同边界，不预先开启全项目重写：

| 共同边界 | 已发现的问题 | 本批检查与通过条件 |
|---|---|---|
| 平台能力及状态归属 | 保存模块使用其他文件才声明的IS_3DS；另一个暂停提示分支在platform.lua:626–627读取World并不提供的game_speed | 清点相关集成变换引入的模块依赖、生成次序、桌面/3DS分支和状态读取；保存使用当前App的operations，暂停使用World的isCurrentSpeed/mustPause。每个状态只由实际拥有者解释，UI不另造权威字段 |
| 所有保存入口的完整事务 | 自动测试直达app.save，真实窗口在进入它之前失败 | 列出新名、已选文件、三槽、覆盖确认/取消、自动保存、保存退出与键盘确认的入口表；逐条追到同一operations→writer→commit→cleanup，核查退出条件、错误去重和重载连续性。异常时先定位最后成功阶段，避免在多个入口分别补救 |
| 测试与正式产品的同一依赖 | 保存测试补IS_3DS全局；test_lua_runtime.py:107–109构造实际World没有的game_speed | 采用最终生成模块、真实strict和真实领域方法验证入口；受控替身只替换已声明的图形/文件/系统服务。禁止由夹具替产品补局部变量或权威状态。先保留旧版可失败的复现，再验证新成功链；两类假设的相关测试一起修正 |

本轮“其余5个IS_3DS文件有声明”仅关闭该变量的同类检索，其他平台引用及入口合同仍待R74-01审查。审查出现新的关联调用链时，先补影响表再实施。没有关联证据的寻路、温度、GPU算法和整个资源系统保持现状。

修复完成的定义包含生产代码与验证方式两部分：真实UI成功、失败及取消都有确定结果，旧问题能被同一测试检出；无需靠用户反复真机试错才能发现缺失依赖。它能降低这一类缺陷复发，无法保证所有未来问题都已消除。
