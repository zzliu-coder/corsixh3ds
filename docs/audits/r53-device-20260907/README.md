# R53 两次真机运行：性能与 emergency 滚图诊断

更新：2026-09-07。供外部独立审查使用；本次工作读取设备和源码、复现缺陷、发布证据，未修改游戏执行代码，未向设备安装新版。

## 结论先读

1. **GPU 路径 FAIL**：两次启动自检均为 1024/1024 像素不一致，随后明确选择软件绘制。用户本次感到“依然卡顿”与这一结果一致。
2. **普通速度仍约 2.16 次画面提交/秒**：第一轮两档自动采样完成，但有效样本属于软件后端。30FPS 目标未达到；正常速度模拟推进仍严重落后。
3. **emergency 计时小窗会阻止地图卷动**：已用真实上游接受事件方法、真实 UIWatch 构造方法和当前 Lua 适配层在电脑端复现。计时小窗被当成限制地图移动的对话框。第一轮后段日志出现对应受限上下文并持续推进日期；具体触发时刻缺少事件日志，逐次真机对应仍为 NOT_PROVEN。
4. 两轮都记录了保存完成、正常退出，没有记录 FATAL。最新存档已私下读回；本轮全部存档逐一重开恢复仍为 NOT_PROVEN。

## 缺陷 A：GPU 启动像素契约仍未通过

**严重程度：阻断 GPU 性能验收；结论 FAIL。**

证据：两份 boot 日志第 10–11 行：
```text
gpu-self-test: result=FAIL pixels=1024 mismatches=1024 ...
gpu: selected=software reason=startup-pixel-contract-failed
```

代码路径：
- [gpu_renderer.cpp](../../../src/3ds/runtime/gpu_renderer.cpp)：startup_self_test，164–193 行；上传图案、四种翻转、GPU 绘制、读画布比较。
- 同文件 gpu_initialize：自检失败释放资源并回退；实际游戏不会使用 GPU 后端。
- [R53 历史施工记录](../../R53_GPU_COORDINATES.md)：官方 tex3ds 对照解决了已知 CPU 上传排列问题；主机对照的通过无法覆盖实际 PICA 渲染目标布局、同步、读取解释和最终 LCD 输出。

当前可证明：设备执行的启动自检失败，GPU 被关闭。
当前不能区分：画布实际画错、自检读取地址/方向/颜色解释错误、或等待/可见性问题。
日志只有 mismatch 总数，没有期望/实际像素、位置和完成状态的细化数据；请勿将其中任意一个猜测宣布为唯一根因。

最小下一步：保留安全回退；对独立固定图案分别记录实际/期望像素及坐标、纹理/画布属性、提交完成状态。
分离“CPU 上传→GPU 采样”“GPU→画布”“画布→双屏”三段，对照 SDK 实际约定，最后让真实医院通过。
禁止为了启用 GPU 绕过自检，禁止把软件回退后的正常画面当作 GPU 验收通过。

## 缺陷 B：倒计时 HUD 被归类为限制滚图的对话框

**严重程度：严重，妨碍 emergency 处置；源码链与电脑复现 FAIL。实际事件逐次对应 NOT_PROVEN。**

完整原因链：
1. 固定上游 `CorsixTH/Lua/dialogs/fullscreen/fax.lua:185–187`：
   接受 emergency 生成 helicopter，并 `ui:addWindow(UIWatch(ui,"emergency"))`；
   244–245 行删除消息并关闭 fax。
2. 上游 `dialogs/watch.lua:33–60`：UIWatch 是 39×79 的常驻计时小窗，`modal_class="open_countdown"`，
   `esc_closes=false`。该类标记用于窗口管理；上游只对 main/fullscreen 改 editing_allowed。
3. 当前 [platform.lua:94–105](../../../lua/3ds/platform.lua) 的 top_window 仅排除 bottom_panel/adviser/subtitles。
   计时器会被选中；407–430 行 inputContext 对其他有 world 的窗口一概返回 dialog。
4. [game_view.cpp:29–69](../../../src/3ds/runtime/game_view.cpp)：Dialog 令 map_context_=false；
   白框仍可在画布内移动，到边缘后不再产生滚地图的剩余位移。
5. [platform.lua:704–711](../../../lua/3ds/platform.lua)：即使收到 pan_camera，Dialog 上下文也不调用 scrollMap。

[电脑复现脚本](reproduce_watch_context.lua)运行真实 UIWatch 构造、真实 UIFax:choice/close 和当前适配器。
图形资源、窗口基础管理及原生接口使用明确的最小替身，没有读取原游戏资源或存档。
[输出](watch-context-result.txt)表明：
- 无计时器：context=world，滚图调用生效；
- 接受 emergency，fax 已关闭、touch down_count=0：剩余计时器使 context=dialog，滚图不生效；
- 移除计时器：world 恢复，滚图重新生效。

这个复现命令退出 0 表示**成功复现产品缺陷**，不能读成产品通过。
初始开院、疫情等同类计时器也走该窗口机制，需一起覆盖；其他 HUD 应按真实行为审查。
不能简单忽略所有窗口，真正的模态窗口、菜单、文本输入和建造仍需保留各自限制。

第一轮 first-boot.log:694/735/785 等显示镜头固定、日期持续推进；696/750/840 行显示 context=4（Dialog）。
本次日志没有 window class、accept_emergency 标记或逐帧摇杆原始样本。
因此已找到可复现的同类根因，尚不能证明每一次用户感到卡住都只由它造成；低帧率、按住触摸、地图边界也需分开判断。
