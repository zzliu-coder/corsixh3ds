# CorsixTH Old 3DS v0.6.1 修复、测试与验收计划

## 1. 目标

把当前 v0.6.0 从“上屏载入图后内存不足、下屏黑屏、自动退出”推进到可以在一台 Old 3DS 上稳定完成以下闭环：

```text
Homebrew Launcher
  → 启动与可见进度
  → 主菜单
  → 载入第一关
  → 双屏显示与完整输入
  → 建房、雇人、治疗
  → 保存、退出、重新启动、读取
  → HOME / 合盖恢复
  → 连续运行 2 小时
```

本计划保留 CorsixTH 0.70.1 和完整原版数据兼容，继续排除裸眼 3D。游戏原版数据留在 SD 卡，不进入源码包和无游戏数据发布包。

## 2. 当前基线

当前真机证据：

- 已运行的新 3DSX SHA-256：`111c97ca28cc580f6a3cb7c002bc556fb088895f558823d316328b4bc93c2bed`。
- Lua 5.4、CorsixTH 0.70.1、SDL 软件渲染器和上屏游戏窗口已经启动。
- `App:init()` 在显示载入图后返回 `not enough memory`。
- 下屏运行时位于 `App:init()` 成功后的 C++ 主循环入口，因此本次没有创建下屏。
- 当前 ELF 使用 libctru 自动堆分配，线性堆会占用大量内存；CorsixTH 的主要负载使用常规堆。
- 全屏 `direct_zoom` 路径仍可能创建一份重复的 640×480 中间缓冲。
- 低内存错误报告器依赖尚未初始化的 `SDL.mainloop`，错误页无法可靠停留。

基线诊断见 `../../hardmac-runs/20260902-1543-readonly-diagnosis/diagnosis.md`。

## 3. 总体验收规则

每个测试只有三种结果：

- `PASS`：证据满足本文全部阈值。
- `FAIL`：已经执行并出现错误、超时、阈值超限或结果不一致。
- `NOT_PROVEN`：没有执行、证据丢失、只通过主机模拟，或真机观察不足。

发布判定：

- 任一 P0 项为 `FAIL` 或 `NOT_PROVEN`，发布状态保持开放。
- 构建成功不能替代真机启动、画面、输入、声音、存档和稳定性证据。
- 屏幕照片可以证明可见结果；二进制身份、内存、性能和错误原因必须由日志、清单和读回哈希证明。
- 每次真机运行单独保存构建身份、部署报告、`boot.log`、游戏日志、测试结果和人工观察。

## 4. 执行路线

### 阶段 0：冻结基线和恢复路径

操作：

1. 为新一轮建立 `work/hardmac-runs/<时间>-v061/`。
2. 从 SD 卡读取并保存当前 3DSX、Lua 补丁、配置、清单、启动日志和游戏日志。
3. 记录远端文件大小和 SHA-256，并与本地候选比较。
4. 保留 `/3ds/corsixth` 的时间戳回滚副本；原版游戏目录和存档目录单独保护。
5. 清点 `/3ds/` 下所有可启动的 CorsixTH 3DSX。正式发布时只保留一个可启动入口；旧文件改成不可启动的回滚扩展名或移出 `/3ds/`。

阶段门槛：

- 当前运行文件、游戏数据目录和回滚目标全部明确：`PASS`。
- 回滚文件经过完整读回哈希验证：`PASS`。
- 任一文件身份不清或没有恢复路径：停止部署。

### 阶段 1：建立启动、内存和错误诊断基础

实现：

1. 记录 `envGetHeapSize()`、`envGetLinearHeapSize()`、常规堆已用量、空闲量、Lua 分配量和最低水位。
2. 删除 `osGetMemRegionFree(MEMREGION_APPLICATION)` 作为“可用堆”的判定用途。
3. 加入单调启动阶段编号：

   ```text
   S00 process entry
   S10 Lua state ready
   S20 config and game path ready
   S30 SDL video and top window ready
   S40 loading image drawn
   S50 audio ready or degraded
   S60 strings ready
   S70 animations and game definitions ready
   S80 UI and 3DS adapter attached
   S90 lower screen ready
   S100 main menu ready
   ```

4. 每个阶段记录时间、常规堆使用量、Lua 使用量和最低剩余量。
5. 在创建昂贵资源之前初始化一个轻量下屏启动页，显示版本、当前阶段和致命错误。
6. 低内存错误页直接使用 3DS/SDL 已有表面和 C++ 事件循环，不调用 Lua `SDL.mainloop`。
7. 错误页至少保留 10 秒，允许按 B 返回 Homebrew，并把完整原因写入 `boot.log`。

自动化测试：

- 阶段编号顺序、耗时计算和内存水位计算单元测试。
- 注入配置缺失、Lua 错误、普通堆 OOM、线性堆 OOM、下屏创建失败。
- 每种错误都必须生成唯一错误码、最后成功阶段和恢复动作。
- 错误路径循环 100 次，Lua 栈和资源计数不得持续增长。

真机验收：

- 启动期间下屏在 2 秒内出现版本和阶段信息。
- `boot.log` 包含实际常规堆、线性堆和 S00～最后阶段。
- 人为制造一个安全的配置错误时，下屏显示同一错误码，B 键能在 3 秒内回到 Homebrew。
- 日志中不得再出现 `attempt to call a nil value (field 'mainloop')`。

### 阶段 2：修正常规堆与线性堆预算

实现：

1. 显式设置线性堆预算，第一候选为 8 MiB；常规堆使用其余可提交内存。
2. 真机记录 top/bottom framebuffer、音频和其他线性分配的峰值。
3. 线性堆峰值加 2 MiB 安全余量后仍超过 8 MiB 时，按实测上调；禁止恢复到未受控的自动分配。
4. 给常规堆、线性堆和 Lua 分配分别设定最低水位告警。
5. 在主菜单和第一关就绪点执行一次有上限的 2 MiB常规堆探针，立即释放，用于证明连续分配余量。

自动化测试：

- ARM ELF 静态检查必须证明 `__ctru_linear_heap_size` 使用明确数值。
- 编译期检查禁止再次使用默认的零值自动分配。
- 内存预算计算、告警和探针成功/失败路径全部覆盖。
- 3DS 交叉构建后读取 ELF 符号并生成 `memory-budget.json`。

真机验收：

- 线性堆实际值与构建清单一致。
- 常规堆总量至少 40 MiB；若 Homebrew 环境提供的总内存更低，必须记录实际上限并重新评估阈值。
- 主菜单就绪时常规堆空闲量至少 8 MiB，2 MiB 探针成功。
- 第一关稳定后常规堆空闲量至少 4 MiB，2 MiB 探针成功。
- 整个启动过程没有 OOM，也没有线性分配失败。

### 阶段 3：删除重复缓冲和启动期高峰

实现：

1. 当缩放为 1.0 且使用 Old 3DS 软件呈现路径时，禁止创建 640×480 `zoom_buffer`。
2. ARM/3DS 路径只保留一个 640×480 主游戏软件表面。
3. 下屏游戏镜像直接从主表面以 2:1 采样到 320×240 下屏表面。
4. 旧管理面板画布改为显式兼容模式才懒加载；默认游戏镜像路径不预分配整张旧面板画布。
5. 载入图和启动期临时纹理在最后一次使用后立即释放。
6. 对动画、字体、声音和 Lua 定义逐阶段记录峰值；只做能够证明安全的延迟加载或释放。

自动化测试：

- 主机模拟器记录所有表面和纹理创建，断言默认路径只有允许的全屏缓冲。
- `direct_zoom=1.0`、全屏和窗口更新组合测试。
- ARM codegen 检查下屏缩放内循环不得出现 64 位除法调用。
- 640×480 → 320×240 像素等价测试覆盖四角、边界、奇偶坐标和随机帧。

真机验收：

- S30、S40、S70、S100 的常规堆变化符合 `memory-budget.json`，没有未解释的 1 MiB 以上跳变。
- 主菜单前不再存在重复 640×480 中间缓冲。
- 上屏载入图之后能够继续进入主菜单。

### 阶段 4：接通新下屏和输入

实现：

1. 启动期间显示轻量进度/错误页；S90 后切换为完整游戏镜像。
2. 默认下屏显示完整 640×480 逻辑画布的精确 2:1 最近邻缩小图。
3. `bottom-screen-panel.txt` 仅保留为人工兼容开关。
4. 镜像尺寸或格式不兼容时显示明确错误码并写日志，禁止静默切回旧面板。
5. 触摸坐标采用 `game_x = touch_x × 2`、`game_y = touch_y × 2`，包含边界钳制和抬起事件。
6. 上屏保持 400×240 的设计视图；下屏负责完整画面和触摸交互。

自动化测试：

- 默认模式、兼容标记模式和格式错误模式三条分支。
- 九点触摸矩阵：四角、四边中点、中心。
- 单击、双击、长按、拖动、反向拖动和取消事件。
- 游戏逻辑帧与下屏镜像帧 CRC 对应关系。

真机验收：

- S90 后下屏显示完整游戏画面，禁止黑屏和旧管理面板。
- 上、下屏连续刷新 10 分钟，无色序错误、旋转、越界、撕裂或随机闪烁。
- 九点触摸全部命中对应的 640×480 逻辑位置，最大误差 2 个逻辑像素。
- 房间拖拽起点、终点和最终网格矩形一致。

### 阶段 5：性能优化与门槛

测量场景统一为主菜单、第一关空医院和第一关 20 个病人。每个场景预热 30 秒、采样 60 秒，排除关卡载入和存档 I/O。

| 场景 | 平均帧时间 PASS | P95 PASS | FAIL 线 |
|---|---:|---:|---:|
| 主菜单 | ≤ 50 ms | ≤ 100 ms | 平均 > 100 ms |
| 空医院 | ≤ 70 ms | ≤ 150 ms | 平均 > 150 ms |
| 20 个病人 | ≤ 100 ms | ≤ 200 ms | 平均 > 200 ms |

额外门槛：

- HBL 启动到首个可见进度：≤ 2 秒。
- HBL 启动到主菜单：≤ 30 秒。
- 主菜单进入第一关可操作状态：≤ 30 秒。
- 普通触摸和按键到可见反馈：≤ 100 ms。
- 任何超过 500 ms 的运行帧必须关联明确的载入、保存或 SD I/O 阶段；普通经营中出现即为 `FAIL`。
- 游戏模拟速度必须独立于渲染帧率，10 分钟游戏计时误差不超过 1%。

自动化测试：

- 帧统计 average/P50/P95/max 和采样窗口测试。
- 固定步长、调度器、present 缩放和 ARM 内循环回归测试。
- 发布报告自动比较基线和候选；任何场景退化超过 10% 阻止发布，除非仍在阈值内且有书面原因。

### 阶段 6：功能与生命周期验收

#### P0-A 启动与退出

- 连续冷启动 10 次，10/10 进入主菜单。
- 连续正常退出 10 次，10/10 在 3 秒内回到 Homebrew。
- 每次日志的版本、二进制短哈希、启动阶段和堆预算一致。
- 不产生新的 Luma ARM11 crash dump。

#### P0-B 第一关完整经营闭环

完成一次：移动镜头 → 建造合法房间 → 放门和必要物品 → 雇佣员工 → 接收病人 → 完成一次诊疗 → 保存 → 退出 → 重新启动 → 读取。

通过标准：

- 关卡状态、资金、房间、员工和病人进度在读取后一致。
- 整个闭环没有 Lua 错误、纹理创建失败或音频线程错误。

#### P0-C 输入

- 圆形摇杆、十字键、A/B/X/Y、L/R、Start、Select 全部测试。
- 在世界、菜单、对话框、建造四种上下文验证含义。
- 按键长按 30 秒后松开，不得继续重复。
- 快速连续输入 100 次，不得出现粘键、幽灵点击或输入队列卡死。

#### P0-D 音频

- UI 音效、环境音、广播和系统音量滑块有效。
- 连续播放 30 分钟，音频欠载计数为 0。
- HOME、合盖和恢复后音频继续或安全重启，禁止持续爆音和卡死。
- DSP firmware 缺失时进入可玩的静音降级状态并显示明确原因。

#### P0-E HOME、合盖和存档安全

- HOME 往返 10 次。
- 合盖 30 秒、5 分钟和30 分钟后恢复。
- 普通状态、菜单、拖建房间、保存期间分别执行一次挂起。
- 恢复后画面、输入、声音和游戏速度正常。
- `.tmp`、`.bak` 和损坏正式存档分别执行恢复测试。
- 正式存档不得为零字节，恢复后必须可读取。

#### P0-F 稳定性

- 第一关连续运行 2 小时。
- 预热 10 分钟后，常规堆使用量相对最低稳定点的持续增长不得超过 1 MiB。
- Lua 分配量不得持续单调增长。
- 没有 OOM、崩溃、死锁、无限载入、音频欠载或输入失效。
- 帧时间始终满足阶段 5 的对应场景门槛。

### 阶段 7：自动构建、部署和取证循环

扩展 `scripts/old3ds_cycle.sh`，形成以下自动链：

```text
识别 FTPD 端点
  → 取回上一轮日志
  → 验证上游补丁契约
  → 主机测试
  → ARM 代码检查
  → 3DS 交叉构建
  → 生成构建清单和内存预算
  → 打包且保留设备游戏/存档数据
  → 上传到隐藏暂存目录
  → 全量或增量读回哈希
  → 原子发布并保留回滚
  → 可选 NetLoader 启动
  → 收集运行日志
  → 生成 PASS/FAIL/NOT_PROVEN 报告
```

快速迭代通道：

- 只运行受影响单元测试、Python 集成测试、ARM 静态检查和增量交叉构建。
- 上传 3DSX、必要 Lua 文件和清单，保留 `game/`、`Saves/` 和用户配置。
- 目标是缩短代码改动到真机启动的时间，不形成发布结论。

发布通道：

- 全新构建目录，禁止复用快速通道产物名称。
- 运行 GCC Debug/Release/Sanitized、Clang、50 次重复状态测试、Python 全套、ARM codegen、上游 API 契约和真实 3DS 交叉构建。
- 生成源码指纹、工具链版本、ELF/3DSX 哈希、文件清单和测试摘要。
- 部署后独立读回 3DSX、Lua 和清单并重新计算哈希。

自动化验收：

- 任一测试或哈希失败时禁止发布。
- 中断上传后，当前 `/3ds/corsixth` 仍保持可启动。
- 回滚演练能够恢复上一个候选并通过哈希校验。
- `/3ds/` 最终只有一个可启动的 CorsixTH 3DSX。
- 每轮都生成 `cycle-summary.json`、工程检查表和设备状态矩阵。

物理操作边界：

- Mac 可以自动构建、上传、读回、启动 NetLoader、抓日志和生成报告。
- Homebrew/FTPD/NetLoader 的首次打开、屏幕视觉判断、按键、触摸、合盖、HOME、声音和电量测试需要真机操作。
- 缺少这些真机观察时，对应项目保持 `NOT_PROVEN`。
